**Swap execution trust boundaries**

This document records the assumptions introduced by the independent swap infrastructure. It is scoped to APT → native USDC on Aptos mainnet and does not constitute an assessment of the entire application.

The protected assets are owner signing authority, wallet balances, server credentials and the integrity of transaction outcomes. The device vault owns private keys. The worker owns provider and gas credentials. Neither a quote provider nor the worker receives the owner's private key.

Provider responses are untrusted transaction proposals. The application and worker independently check asset identity, router identity, argument shape, recipient, input/output bounds, slippage and the supported zero-fee multiplier. Both encode the same payload and compare its hash. Provider-supplied raw transactions and signing messages are ignored. Unknown layouts and unsupported routes fail closed.

The integration trusts the reviewed deployment of Panora's router to enforce its declared limits and the Aptos node to report simulation and committed execution accurately. Matching an ABI does not establish that an upgraded contract retains the same semantics. Deployment or fee-policy changes therefore require new review and fixtures. Simulated net APT and USDC movements are checked before owner authorization; simulation does not guarantee execution against future chain state.

Owner authorization is scoped to an immutable quote, its wallet and profile, its expiry and the current foreground visit. A biometric prompt grants no general background signing capability. Profile and foreground state are rechecked after authorization and before submission. The shared submission gate prevents simultaneous authorization by the swap, Decibel and fee-top-up paths. Delegated trading keys cannot execute owner swaps.

The worker signs a separate, domain-separated quote authorization bound to the wallet, payload hash and expiry. Sponsorship accepts that exact payload only on the owner route, with bounded gas and transaction expiry. Durable quote-use reservation prevents one authorization from sponsoring different signed transactions. Existing fingerprint records correlate retries and status reads with the original submission. The session-signing secret remains a trusted server credential; rotation invalidates outstanding quote authorizations.

The signed reference is persisted before broadcast. A separate operation record retains final outcomes after pending-journal cleanup and links sponsorship fingerprints to confirmed hashes. Lost responses remain unresolved and are never automatically retried or converted into self-payment. A known rejection before submission permits a separately authorized self-paid attempt. Database or operation-history corruption fails closed rather than discarding potentially submitted operations. History pruning retains every unresolved operation.

Recovery depends on access to the worker's sponsorship record or the transaction hash on Aptos. An unresolvable fingerprint remains pending; elapsed quote expiry alone is insufficient evidence that the transaction did not commit. A future recovery mechanism must establish non-execution before releasing that operation for replacement.

Quote service availability is bounded by authenticated owner and IP rate limits, provider deadlines, response-size limits and per-isolate transport backoff. Provider failures affect swap availability without introducing a fallback route after authorization. Exact arithmetic and conservative gas reserves prevent display rounding or sponsorship loss from exhausting the approved spend budget.

The worker enables quotes with the configured Panora API key. Gas Station policy is required only for sponsorship; a definite rejection permits explicit user-paid gas. Live exact-input and exact-output quotes and one real 2 APT mainnet swap have been verified. That swap completed with self-paid gas after a definitive sponsorship rejection.

The Transfer sheet treats swap and deposit as separate authorizations. It requests only a USDC shortfall, uses exact balances, and retains APT for both network-fee budgets when suggesting a maximum. Balances are reread before quoting, execution and deposit; a failed read is unavailable, never assumed zero. Capacity estimates are advisory because balances and fees can change; simulation and on-chain input limits still enforce execution bounds. A completed swap returns to Transfer without automatically depositing or replacing an uncertain transaction. Profile/account changes invalidate the quote. Input changes cancel pending quote requests, and request revisions discard stale responses even when cancellation is not cooperative. Automatic quote refresh is limited to the visible route and pauses during execution; it never authorizes or submits a swap. Reopening the sheet restores unresolved operations before offering another swap.

Quote freshness uses a bounded remaining lifetime from the authenticated worker response. The client counts it from its local request start, so response time cannot extend the signing window and fixed device clock skew cannot reject a valid fast response. The original worker expiry remains in the signed transaction and sponsorship authorization. Automatic retries obtain quotes only; they never repeat execution.

A fallback provider request can select an FA-capable source when the initial route has unsupported coin types. This happens before quote authorization, shares the original request deadline, and applies the same independent payload checks. It does not widen the accepted coin types or change a signed transaction.


Background fee preparation is read-only on chain: it builds and simulates unsigned transactions without biometric authorization, transaction signatures, quote-use reservations or submission. The resulting fee payer, estimated gas, maximum reserve and exact unsigned transaction remain bound to the retained quote. The app revalidates effects, available funds, profile, foreground visit and expiry at confirmation. Old persisted operation records may lack fee plans for compatibility, but new execution requires a reviewed fee plan. The worker's sponsorship availability route is owner-authenticated and reports deployment policy, not a reserved provider budget. Its positive result cannot guarantee future acceptance; the current failing provider configuration is disabled explicitly. Availability-read failure selects a disclosed self-pay quote before signing, never a replacement for a potentially submitted transaction.


Funding intent and swap intent are separate. Transfer amounts, including blank input, survive swap edits and completion unchanged. The swap editor initially receives only the transfer shortfall, then quotes the exact APT input or USDC output the user edits; existing USDC never blocks a voluntary swap. A newly observed pre-transfer shortfall returns control to the unchanged form before any authorization or deposit call. Balance refreshes are read-only and silent, with a 30-second freshness bound for retained snapshots, a 20-second read deadline, foreground/profile binding and revision checks against late results. Every execution still rechecks available funds independently of displayed values.


The original funding-transfer confirmation now authorizes a bounded automatic gas fallback. Only Deposit, Withdraw and the reviewed follow-up USDC TransferCollateral command may use `FeePayment.AUTOMATIC`. The sponsor is attempted once; a definite rejection with a sufficient full gas reserve permits one self-paid attempt under the same command, wallet, profile, visit, gas price, gas limit and expiration. Both attempts are journaled independently before broadcast. Any transport uncertainty, unresolved journal record, profile/foreground change, expired authorization, unsupported gas price or insufficient reserve stops replacement. The policy is not available to trades, setup or swaps. Fee estimates are exposed before fresh transaction authorization, and confirmed sponsorship coverage is metadata from an accepted sponsorship, not a promise made from configuration.
